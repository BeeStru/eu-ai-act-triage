convention, per PLAN.md section 4, because the design of a manual release
discipline is whatever the repository writes down as its rule. The whole
tracked tree was searched for any statement of a versioning or tagging

What the output shows. No tracked file states a versioning or tagging rule:
the word-bounded search for "tag", "tags", "tagged" or "tagging" returns
nothing (exit 1), and the only hit for the broader pattern is question 2 of
the third-party due-diligence template, which asks a vendor about its release
cadence and says nothing about this repository. Every "version" hit is the
Python matrix, a prose reference to tool or model versions or to "versioned
data files", a questionnaire item, or the version number itself and its use
in the audit-record string. The version is recorded in
three places that agree: `pyproject.toml` line 7 and `__init__.py` line 3
both read `0.5.0`, and `CHANGELOG.md` carries one heading per release,
0.1.0 to 0.5.0. Within the published tree the practice is visible in those
records, but no written rule for it is present.

The documented convention is rule D5 of the execution plan, line 405 to 409:
"A release commit contains exactly: the two version-string bumps, the
changelog entry, nothing else." The plan's "Version arc" paragraph, line 75
to 81, adds the tag: "A release = one commit that bumps both version
strings, appends the changelog entry, and gets an annotated tag `vX.Y.0`",
and "The two version strings must always be equal; check before each
release commit." The two version strings are the ones found in the
published tree above, `pyproject.toml` and `src/aiact_triage/__init__.py`.

Observation, not a deficiency, per the ruling: the convention sits outside
the published tree. The plan states of itself that it "is NEVER committed to
the repository", and no tracked file in the clone has a name matching
`execution_plan` (count 0).
