# WP-CA04-design-20260827

**Control.** CA-04, packaged-data integrity check in CI (non-editable
reinstall).

**Test method and reason.** Inspection of the workflow step, because the control
is automated and its design is the step's own instructions. Four elements
checked per PLAN.md section 4: uninstall, non-editable reinstall, import of
`aiact_triage.rules`, and the `timeline()` call executed from `/tmp`. The
inspection is extended by one supplementary check not in the method, that the
imported callable the step names exists in the package, because a step naming a
callable that does not exist would be a design defect the file alone cannot
show. Deviation noted; the supplementary check is recorded separately below.

**Population and regime.** Not applicable, design test. The object under test is
a fresh clone of `https://github.com/beestru/eu-ai-act-triage` taken at
2026-08-27 11:17:28 UTC, `main` at commit
`7aab9f95065f9cf69cbdefe5a9aed64c361386ce`.

**Procedure executed.**
```
cd repo_under_test
cat .github/workflows/tests.yml
grep -n 'def timeline' src/aiact_triage/rules.py
```

**Evidence.**

The step under inspection, quoted from the workflow file evidenced in full at
WP-CA03-design-20260827:
```
      - name: prove non-editable install carries the rule data
        run: |
          pip uninstall -y aiact-triage
          pip install .
          cd /tmp && python -c "import aiact_triage.rules as r; r.timeline(); print('packaged data ok')"
```

Supplementary check, the callable the step imports:
```
=== grep -n 'def timeline' src/aiact_triage/rules.py ===
25:def timeline() -> dict[str, dict]:
31:def timeline_meta() -> dict:
```

**Executed.** 2026-08-27, 12:20 to 12:21 BST.

**Conclusion.** Design effective: the step uninstalls the editable install,
reinstalls the package non-editably with `pip install .`, and then changes to
`/tmp` before importing `aiact_triage.rules` and calling `timeline()`, which is
defined at line 25 of that module. The design is good for one specific reason
worth stating: running the import from `/tmp` puts the working directory
outside the checkout, so the source tree cannot satisfy the import and the
rule data can only come from the installed package. It therefore tests the
artefact a user receives rather than the developer's checkout, which is the
failure mode the control exists to catch, a package that imports cleanly in
development but ships without its `data/*.json` payload. Whether the step ran
and passed is the operating test and is not addressed here.
